## 🎯 Покриття вимог та рівнів складності

### 🟢 Рівень 1 (L1) — Перегляд учасників та підрахунок суми
- **UI & API:**
  - Owner створює бронювання, запрошує гостей, гості приєднуються та додають страви.
  - Перевірка, що Owner бачить усіх учасників, їхні страви, кількості та суму по кожному.
  - Динамічна зміна загальної суми при оновленні кошика гостем.
  - Перевірка статусів: учасники з підтвердженим/непідтвердженим кошиком, а також учасники без страв.
  - Перевірка поведінки для групи без учасників (`participants: []`, `total: 0`).
- **Security & Access Control:**
  - Обмеження доступу: список бачить лише Owner цієї групи (повернення помилки/заборона для не-Owner, чужого клієнта, офіціанта чи неавторизованого користувача).
  - Оброка запитів до неіснуючої групи (404).

### 🔵 Рівень 2 (L2) — Підтвердження консолідованого pre-order
- **Позитивні сценарії (UI & API):**
  - Успішне підтвердження: Owner підтверджує консолідований pre-order, статус міняється на `SubmittedByCustomer` / `Submitted`.
  - Консолідація: однакові страви від різних гостей об'єднуються з підсумковою кількістю.
  - Фільтрація: беруться лише підтверджені кошики (непідтверджені кошики не враховуються).
  - Перевірка офіціантом: офіціант бачить підтверджене замовлення зі складом, який затвердив Owner.
- **Негативні сценарії (окремі перевірки):**
  - Спроба підтвердження, якщо немає жодного підтвердженого кошика.
  - Спроба підтвердження, якщо у підтверджених кошиках немає жодної страви.
  - Спроба підтвердження неіснуючого замовлення/групи.
  - Спроба повторного підтвердження вже підтвердженої групи.
  - Спроба підтвердження користувачем, який не є Owner-ом.

### 🟣 Рівень 3 (L3) — Видалення учасника з групи
- **UI & API сценарії:**
  - Видалення одного учасника з кількох: список оновлюється, загальна сума перераховується.
  - Видалення учасника, який уже підтвердив кошик, та видалення останнього учасника.
- **API validation:**
  - Спроба видалення учасника з іншої групи (400).
  - Спроба видалення неіснуючого учасника (404).
  - Спроба видалення користувачем, який не є Owner-ом.
- **End-to-End сценарій:**
  - Кілька гостей додають страви → Owner переглядає → видаляє одного учасника → підтверджує → офіціант бачить замовлення без видаленого учасника.

## 🛠️ Архітектура проєкту

- **BDD Framework:** Reqnroll (Gherkin сценарії у папці `Features/`)
- **UI Engine:** Playwright .NET (Page Objects / Screenplay у папці `Ui/`)
- **API Layer:** REST API Clients для авторизації, підготовки тестових даних та прибирання (`Api/`)
- **Data Isolation:** Унікальні ідентифікатори та динамічна генерація дат (`now + N`) для уникнення флейків.
